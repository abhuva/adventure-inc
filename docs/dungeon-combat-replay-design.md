# Dungeon Combat Replay Design

## Purpose

Define the deterministic dungeon combat replay model.

Combat replay is an inspection tool. It is not the game clock and it does not mutate authoritative game state while playing.

## Core Rule

Dungeon simulation runs instantly and produces:

- final estimate data
- deterministic transcript
- structured combat replay timeline

The replay viewer consumes the stored timeline at a comfortable UI speed.

Automation and committed operations use the final estimate immediately. They do not wait for replay playback.

## Time Separation

There are two separate time domains:

- `game time`: hours/days used for travel, workers, operations, recovery, and automation.
- `combat replay time`: ordered inspection events generated by the deterministic resolver.

Replay playback must not call `advanceTime()` and must not apply rewards, damage, XP, or resource changes.

## Current Combat Resolver

Combat now uses per-actor timelines instead of one aggregate party attack per round.

Party actors are created from current roster members:

- HP/max HP from `heroStats()`
- ATK/DEF/utility from `heroStats()`
- initiative from utility, travel speed, and stable party order
- speed from utility and travel speed
- portrait from the character atlas

Enemy actors are created from dungeon node enemy data:

- HP
- ATK
- optional DEF
- optional initiative/speed
- deterministic script

The scheduler repeatedly selects the living actor with the lowest `nextActionAt`.

Tie-breakers:

1. lower `nextActionAt`
2. higher initiative
3. party before enemy
4. stable actor ID

After an actor acts, its next action time advances by action recovery reduced by speed.

## Current Actions

Party actions are selected deterministically from strategy and actor state:

- `balanced`: can heal wounded allies.
- `guarded`: can use Guard Stance before scripted heavy enemy actions.
- `burst`: can use a slower high-power attack.
- fallback: basic attack.

Enemy actions follow the node's deterministic script.

## Replay Timeline Events

Events include:

- icon/type
- text
- active actor ID
- target actor ID
- party actor HP/stat snapshot
- enemy actor HP/stat snapshot

The Dungeon tab replay UI displays:

- full-width timeline slider with one step per event
- party actor cards
- enemy actor cards
- action icon
- event text
- recent event log
- first/prev/play/next/last controls
- playback speed control

Autoplay advances the replay cursor on a UI timer and redraws only the replay panel. It does not rerender or tick the full game simulation.

## Current Limitations

- Enemy side is still one actor per combat node.
- Per-character learned skills do not yet define combat actions directly.
- Party damage from hazards is distributed deterministically but is still a prototype rule.
- Committed operations still restore party members after the operation, preserving the previous prototype recovery behavior.
- Combat timeline event time is ordered for replay, not balanced final combat seconds.

## Future Work

- Move combat skills into data definitions.
- Add per-character action-plan editing.
- Add multi-enemy nodes.
- Persist injury state through operations once recovery rules are redesigned.
- Let gear, skills, and Temple effects contribute to specific action properties.
